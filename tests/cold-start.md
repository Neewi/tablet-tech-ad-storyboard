# 美工交付前的独立试跑

供维护者验收一个版本。日常广告制作只读取制作流程。测试产物保存在被 Git 忽略的工作目录。

1. 记下 Git 提交号，从该提交导出或克隆干净项目，在**新对话**中打开。可见业务资料仅限这个提交的文件、美工当次输入的实售信息和原始产品素材。不要附理想宫格、竞品截图、失败分析或具体镜头答案。不要把测试量表和判定标准粘给执行者。
2. 用同一句普通业务请求开两个独立对话。第一次规划四段并实际生成最难的一张；保存第一次出图、原始生图词、所用参考图、视频词和执行者的审核结果。第二次预算紧张时先只看文字候选；要判断出图稳定性，需在第二次也实际生成。计数时区分首轮和返修后结果。
3. 参考输入：为 TAB9 制作视频素材，Temu 不含充电头，参数上屏。给出一份当批确认的规格和准确显示文字。只限制本次预算为一张宫格，其余由 skill 决定。再用一个备选型号测试无参数、含充电头分支。配色、片段编号和概念机制均不给提示。
4. 先给另一位审阅者看真实宫格，隐藏提示词、策划表和执行者结论。请其用格号指出商品起态、可追踪的物体、空间/尺度发生变化的中间态和到达结果。主概念组还要能指出哪一格由概念结构占据主要画面。若只能指认文字变化或屏幕换页，此项失败。再单独对照原图检查商品与配件，逐字核对当批英文和剪辑保留窗口。
5. 将盲审与生产者结论比较。图不合格却被生产者放行，修审核规则；生图词本身只描述展台和屏内卡片，修镜头策划与逐格描述；词有明确空间状态而图漏画，执行定向返修。只改失败环节，换新对话重新测。内部记录首轮失败与返修次数，不能只保存最好的一张。
6. 比较两次运行时先去掉配色与形容词，再比较开场动作、概念机制、镜头路线和回到实体的方式。文字候选有区别只能证明策划有变化。任一首张通过也只代表该主段；完整交付另验四段、使用场景、套装与裁后时长。动态再由美工用一张已过审宫格在 Gemini 生成一次，逐帧检查跨帧身份，并实时播放判断速度曲线和转场。

每次记录版本、正常输入、调用范围、第一次图片、盲审依据、参数和外观结论、返修原因及视频验证状态。此记录用于离线验收，不成为 skill 运行时的历史库。

盲审分两次回答：先写空间和商品的关系，再写画面可支持的功能类别及格号。最后揭开策划核对该类别与本段主卖点是否一致。两项分别判定，不能因为穿屏成立就给存储或计算的表达一起判通过。

CPU 回归用例：同批仅确认英文“Octa-core Processor”。完整方案须定位处理器组；抽测该段，首图检查可辨芯片、卡面原文与处理前后状态。仅交付“照片碎片并行合成→整机旁显示 CPU 和 RAM”的方案应判 CPU 待修。无参数版本不复制该英文，跨型号不继承旧 CPU 型号。
